# 09·12 · Blob / Object Storage

> **Why this exists:** any design involving files, images, video or backups. ⭐ **And it contains the single
> highest-value one-liner in this phase: never proxy file bytes through your application.**

---

## Reference

### ⭐ The rule

> ⭐ **UPLOAD DIRECT TO STORAGE VIA A PRESIGNED URL. DOWNLOAD VIA A CDN. Your application handles
> PERMISSION and METADATA — never the bytes.**

```
❌  client ──▶ your app ──▶ S3        every byte crosses your servers
✅  client ──▶ your app   "may I?"    → a presigned URL
    client ──▶ S3 direct  (bytes)
    client ──▶ your app   "done"      → record metadata
```

⭐ **Why it matters so much:** proxying means your app's bandwidth, memory and request timeouts scale with
file size. **A 5 GB upload occupies a worker for minutes**; a hundred of them exhaust your pool
([Phase 7](../../phase-07-reliability/notes/04-bulkheads-and-isolation.md)). ⭐ **Presigned URLs move that
entire problem to infrastructure built for it, and cost you one cheap API call.**

### Presigned URLs

**A time-limited, signed URL granting one specific operation on one specific key.**

⭐ **Constrain them, don't just issue them:** short expiry (minutes) · **the exact key**, generated by *you*
(⚠️ **never let the client choose the path** — that's a path-traversal / overwrite bug) · **content-type and
`content-length-range`** so a "profile photo" can't be a 10 GB file · **conditions on the upload policy**.

⚠️ **The gap you must close: the object exists before your app knows about it.** ⭐ **Handle it with a
storage EVENT (S3 → SNS/SQS/Lambda) rather than trusting a client callback**, which may never arrive. Then
reconcile: **orphaned objects with no metadata row get swept by a lifecycle rule.**

### ⭐ Multipart & resumable uploads

⚠️ **A single-request 5 GB upload that fails at 99% starts over.** On mobile, it will fail.

⭐ **Split into parts (5–100 MB), upload them independently and in parallel, then COMPLETE** with the list of
part ETags. **Retry only the failed part.** ⭐ **Parallelism is a bonus; resumability is the point.**

⚠️ **Incomplete multipart uploads keep costing you money invisibly** — parts are stored but the object
doesn't exist, so they don't show in a normal listing. ⭐ **A lifecycle rule to abort incomplete uploads
after N days is a genuinely common forgotten cost.**

### ⭐ Content-addressed storage & dedupe

**Key the object by the hash of its content** (`sha256(bytes)`):

| | |
|---|---|
| ⭐ **Automatic dedupe** — the same file uploaded a million times is stored once | |
| ⭐ **Integrity for free** — the key *is* the checksum | |
| **Immutability** — content can't change under a key, so it's ⭐ **infinitely cacheable** |
| ⭐ **Cheap client-side skip** — hash first, and if it exists, skip the upload entirely |

⚠️ **The costs:** you need a **reference count** before you can ever delete (⭐ *whose file is it when three
users uploaded it?*) · no meaningful key ordering · ⭐ **and a privacy wrinkle — "delete my data" doesn't
delete a block another user still references.** Encrypt per-owner if that matters.

### Storage classes & lifecycle

| Class | Use | Catch |
|---|---|---|
| **Standard** | active | |
| **Infrequent Access** | older, still instant | ⚠️ **per-GB retrieval fee + a minimum storage duration** |
| ⭐ **Glacier / Archive** | compliance, backups | ⚠️ **retrieval takes minutes to HOURS, and costs real money** |
| **Intelligent tiering** | unknown patterns | a small monitoring fee |

⭐ **Lifecycle rules automate the transitions** — and they're where the savings are. ⚠️ **But model the
retrieval cost before archiving anything you might actually need**: a "cheap" archive you restore monthly is
more expensive than Standard. ⭐ **And versioning + no lifecycle rule = you are paying for every version of
every object forever**, which is the classic surprise bill.

### ⭐ CDN in front of blobs

⭐ **Always, for anything user-facing.** Latency, egress cost (⚠️ **cloud egress is often the largest line
item** — CDN egress is cheaper than origin egress), and origin offload.

| | |
|---|---|
| **Public content** | long `Cache-Control`, ⭐ **content-hashed filenames so you never need to invalidate** |
| ⭐ **Private content** | **signed CDN URLs / signed cookies** — ⭐ **so authorisation still doesn't touch your app** on the hot path |
| **Range requests** | ⭐ essential for video seeking and resumable downloads |

⚠️ **Cache invalidation is slow and sometimes costly.** ⭐ **Version the URL instead of purging** — this is
the same immutability trick as content addressing.

### The metadata store

⭐ **Blob storage holds bytes; a database holds truth.** Keep `(id, key, owner, size, content_type, hash,
status, created_at)` in Postgres. ⚠️ **`status` matters** — `pending → uploaded → processed` — because the
upload is asynchronous and a row without it can't distinguish "still uploading" from "failed".

⭐ **Listing objects by scanning the bucket is an anti-pattern** — it's slow, paginated, eventually
consistent, and can't be joined. **Query your database.**

### Other things worth a sentence

**Encryption at rest** (SSE-S3/KMS; customer-managed keys when compliance asks) · **object lock / WORM** for
compliance and ⭐ **ransomware resistance** · ⚠️ **S3 is now strongly read-after-write consistent** (it wasn't
historically — old advice is stale) · ⭐ **egress cost is the thing that surprises people**, not storage cost.
