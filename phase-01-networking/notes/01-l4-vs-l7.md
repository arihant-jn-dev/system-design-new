# 01 · L4 vs L7 — The Only OSI Distinction You'll Use

> **Why this exists:** you will not be asked to recite seven OSI layers. You *will* be asked, constantly,
> whether something happens at L4 or L7 — because it determines what a component can **see**, and therefore
> what it can **do**. This note is short and you should know it cold.

---

## Reference

### The seven layers, honestly

| Layer | Name | Do you need it? |
|---|---|---|
| 7 | Application (HTTP, gRPC, DNS) | **Yes** |
| 6 | Presentation | No — folded into 7 in practice |
| 5 | Session | No — folded into 7 in practice |
| **4** | **Transport (TCP, UDP)** | **Yes** |
| 3 | Network (IP, routing) | Occasionally (anycast, CIDR) |
| 2 | Data link (Ethernet, MAC) | Rarely |
| 1 | Physical | No |

**In practice there are two layers that matter: 4 and 7.** Learn those properly and treat the rest as trivia.

### The distinction in one line

| | **L4 (transport)** | **L7 (application)** |
|---|---|---|
| **Sees** | IP addresses, ports, TCP flags | **The full request**: method, path, headers, cookies, body |
| **Doesn't see** | Anything inside the payload | — |
| **Decides using** | 5-tuple (src IP, src port, dst IP, dst port, protocol) | URL path, `Host`, headers, JWT claims, user ID |
| **TLS** | Passes encrypted bytes through untouched | Usually **terminates** TLS (must decrypt to read) |
| **Cost** | Very cheap — near line rate, millions of conn/s | Higher — parse, buffer, re-encrypt |
| **Latency added** | ~microseconds | ~sub-millisecond, but real |
| **Connection model** | One TCP connection proxied end to end | **Two** connections: client↔proxy and proxy↔server |

### What each unlocks

| Capability | L4 | L7 | Why |
|---|---|---|---|
| Round-robin / least-connections | ✅ | ✅ | Doesn't need request content |
| Route by **URL path** (`/api` → svc-a) | ❌ | ✅ | Path is inside HTTP |
| Route by **Host** header (virtual hosts) | ❌ | ✅ | Header is L7 |
| **Canary by header/cookie** ("5% of users") | ❌ | ✅ | Needs to read the request |
| **Retry a failed request** | ❌ | ✅ | L4 doesn't know where a request starts or ends |
| Per-request load balancing (HTTP/2 streams) | ❌ | ✅ | L4 balances *connections*, not requests |
| Rate limit per user/API key | ❌ | ✅ | Identity lives in headers |
| Response caching | ❌ | ✅ | Must understand the request |
| Compression, header rewriting | ❌ | ✅ | — |
| Balance **non-HTTP** traffic (Postgres, Redis, SMTP) | ✅ | ❌ | L7 proxies are protocol-specific |
| **End-to-end encryption preserved** | ✅ | ❌ | L7 must decrypt |
| Extreme throughput / low cost | ✅ | ➖ | Nothing to parse |

### The one that catches people

**L4 balances connections; L7 balances requests.** With HTTP/1.1 and short connections these look similar. But
with **HTTP/2 or gRPC**, a client opens *one long-lived connection* and multiplexes thousands of requests over
it. An L4 balancer pins that whole connection to one backend — so:

> **gRPC behind an L4 load balancer gives you catastrophically uneven load.** Ten clients, ten connections,
> ten backends — but if one client sends 90% of the traffic, one backend gets 90% of the work, forever.

**This is why service meshes and gRPC deployments need L7 (Envoy, gRPC-native LB, or client-side balancing).**
It's an excellent thing to raise unprompted in a microservices design.

### Where you meet each in a real request path

```
Client
  │
  ├─ DNS (L7 app protocol, usually over UDP at L4)
  │
  ├─ Anycast routing ─────────────── L3
  │
  ├─ Cloud NLB / IPVS ────────────── L4   cheap, fast, protocol-agnostic
  │
  ├─ CDN / ALB / nginx / Envoy ───── L7   TLS termination, path routing, caching, WAF
  │
  ├─ API Gateway ────────────────── L7   authn, rate limiting, request shaping
  │
  ├─ Service mesh sidecar ───────── L7   mTLS, retries, circuit breaking, tracing
  │
  └─ Your service
```

**The common production pattern: L4 at the very edge (cheap, absorbs volume and DDoS), L7 behind it (smart
routing).** Being able to say that sentence — and say *why* — is the whole point of this note.

### TLS termination — where, and the tradeoff

| Approach | What happens | Use when |
|---|---|---|
| **Terminate at edge** (CDN/LB) | Decrypt once; plaintext (or re-encrypted) inside | Default. Enables caching, routing, WAF. |
| **Passthrough** (L4) | Encrypted end to end to the backend | Compliance/regulatory; backend needs the client cert |
| **Re-encrypt** | Decrypt at edge, re-encrypt to backend | Best of both — the common compliance answer |
| **mTLS everywhere** (mesh) | Every hop mutually authenticated | Zero-trust internal networks |

**The tradeoff to state out loud:** terminating early buys you routing, caching and observability; it costs
you end-to-end encryption, so the internal network becomes part of your trust boundary. Re-encryption is the
usual compromise.
